# Amazon S3 ストレージ設計

## 概要

本構成では、ローカル環境のデータをAmazon S3へ自動バックアップし、
データ保護とストレージコストの最適化を実現します。

本設計では、以下の点を重視しています。

* 誤操作による上書き・削除からの保護
* 長期保存時のストレージコスト最適化
* バックアップ実行権限と管理者権限の分離
* 過去バージョンを利用したデータ復元
* IAMの最小権限の原則（Least Privilege）

---

## S3 Versioning

バックアップ用S3バケットでは、S3 Versioningを利用します。

同一オブジェクトの複数バージョンを保持することで、
誤ってファイルを上書きした場合でも、過去のバージョンから復元できます。

### 例

```text
report.pdf
├── Version 1
├── Version 2
└── Version 3 (current)
```

過去バージョンを保持することで、
誤った上書きや更新が発生した場合でも、
必要に応じて以前の状態へ復元できるようにします。

---

## Lifecycle Policy

バックアップデータを長期間保存する際のストレージコストを抑えるため、
S3 Lifecycle Policyを利用します。

本構成では、オブジェクトの経過日数に応じて、
以下のストレージクラスへ移行する設計とします。

| 経過日数    | ストレージクラス                      |
| ------- | ----------------------------- |
| 0〜29日   | S3 Standard                   |
| 30〜179日 | S3 Standard-IA                |
| 180日以降  | S3 Glacier Flexible Retrieval |

最近作成されたバックアップデータはS3 Standardに保存し、
すぐにアクセスできる状態を維持します。

30日経過後はS3 Standard-IAへ移行し、
アクセス頻度が低下したデータのストレージコストを削減します。

180日経過後はS3 Glacier Flexible Retrievalへ移行し、
長期保管用のバックアップデータとして低コストで保存します。

これにより、
バックアップデータの可用性を維持しながら、
長期保存にかかるストレージコストを最適化します。

### 128KB未満のオブジェクト

Amazon S3 Lifecycleでは、128KB未満のオブジェクトは
デフォルトではストレージクラス移行の対象になりません。

本構成のLifecycle PolicyではオブジェクトサイズによるFilterを指定していないため、
128KB未満の小さなファイルはS3 Standardに保持されます。

バックアップ対象には設定ファイルやテキストファイルなど、
小容量のオブジェクトが含まれる可能性があります。

小容量オブジェクトを低コストストレージへ移行すると、
オブジェクトごとに発生する移行リクエスト料金によって、
ストレージコスト削減効果を上回る場合があります。

そのため本構成では、
128KB未満のオブジェクトについてはAWSのデフォルト動作を利用し、
サイズFilterによる強制的なストレージクラス移行は行わない設計としています。

### 未完了Multipart Uploadのクリーンアップ

大容量ファイルのアップロードでは、
AWS CLIがMultipart Uploadを利用する場合があります。

ネットワーク切断や処理中断などによってMultipart Uploadが完了しなかった場合、
アップロード済みのパーツがS3上に残る可能性があります。

本構成ではLifecycle Policyに以下の設定を追加しています。

```json
"AbortIncompleteMultipartUpload": {
  "DaysAfterInitiation": 7
}
```

これにより、開始から7日経過しても完了していないMultipart Uploadを
自動的にAbortする構成としています。

未完了アップロードのパーツが長期間残ることを防ぎ、
不要なストレージ使用量の増加を抑制します。

なお、この設定は完了済みのオブジェクトを削除するものではありません。
---

## 非現行バージョンの保持

S3 Versioningが有効な状態でオブジェクトを上書きすると、
以前のオブジェクトは非現行バージョン（Noncurrent Version）として保持されます。

本構成では、非現行バージョンを90日間保持した後、
Lifecycle Policyによって削除する設計とします。

```text
Current Version
      │
      │ 上書き
      ▼
Noncurrent Version
      │
      │ 90日間保持
      ▼
Expiration
```

これにより、
一定期間は過去バージョンから復元できる状態を維持しながら、
不要な旧バージョンが無期限に蓄積することを防ぎます。

## 誤削除対策

バックアップデータの意図しない削除を防止するため、
複数の対策を実施します。

### aws s3 sync の設定

バックアップスクリプトでは、
`aws s3 sync` の `--delete` オプションを使用しません。

そのため、
ローカル環境からファイルを削除しても、
次回のバックアップ実行時にS3上のオブジェクトが自動削除されることはありません。

```text
ローカルファイル削除
        │
        ▼
次回バックアップ実行
        │
        ▼
S3上のバックアップは保持
```

ローカル側の誤操作が、
そのままバックアップデータの削除につながらない構成とします。

---

## IAMによる削除権限の制限

バックアップ処理で使用するIAMポリシーには、
以下の権限を付与しません。

```text
s3:DeleteObject
```

これにより、
バックアップ処理を実行するIAMユーザーから、
S3上のオブジェクトを削除できないようにします。

`aws s3 sync --delete` を使用しないことと、
IAMで削除権限を付与しないことを組み合わせることで、
誤削除に対する多層的な対策とします。

---

## IAM セキュリティ設計

バックアップ処理で使用するIAM権限は、
最小権限の原則（Least Privilege）に基づいて設計します。

バックアップ実行に必要な操作のみを許可します。

### 許可する主な操作

* S3バケット内のオブジェクト一覧取得
* S3バケットのリージョン情報取得
* S3へのオブジェクトアップロード
* Multipart Uploadに必要な操作

一方で、
以下の管理操作はバックアップ用IAMポリシーから除外します。

### 許可しない主な操作

* S3オブジェクトの削除
* S3バケットの削除
* Lifecycle Policyの変更
* Versioning設定の変更
* Bucket Policyの変更

これにより、
バックアップを実行するための権限と、
S3を管理するための権限を分離します。

バックアップ処理に不要な権限を与えないことで、
認証情報が意図せず使用された場合の影響範囲も限定します。

## バックアップ対象

本構成では、
以下のローカルディレクトリをバックアップ対象とします。

```text
~/Documents
~/Desktop
~/Pictures
~/Downloads
```

バックアップ対象は、
`scripts/s3-backup.sh` 内で管理します。

バックアップスクリプトでは、
各ディレクトリをAmazon S3上の対応するプレフィックスへ同期します。

### 例

```text
~/Documents
      │
      ▼
s3://<BUCKET_NAME>/Documents/

~/Pictures
      │
      ▼
s3://<BUCKET_NAME>/Pictures/
```

## バックアップ自動化

バックアップ処理の自動実行には、
macOSの`launchd`を利用します。

本構成では、
毎日22:00にバックアップスクリプトを実行する設計とします。

```text
毎日 22:00
    │
    ▼
launchd
    │
    ▼
s3-backup.sh
    │
    ▼
AWS CLI
    │
    ▼
Amazon S3
```

自動実行設定は、
以下のファイルで管理します。

```text
launchd/io.github.mahiro0323.s3-backup-automation.plist
```

バックアップスクリプト本体は、
以下のファイルで管理します。

```text
scripts/s3-backup.sh
```

---

## ログ管理

`launchd`によるバックアップ実行時の標準出力とエラー出力は、
それぞれ別のログファイルへ出力します。

### 標準出力

```text
/tmp/s3-backup-automation.log
```

### エラー出力

```text
/tmp/s3-backup-automation-error.log
```

正常実行時のログとエラーログを分離することで、
障害発生時の原因調査を行いやすくします。

---

## 認証情報の管理

AWSの認証情報や実際のS3バケット名など、
公開すべきでない情報はGitHubリポジトリへ保存しません。

実環境用の設定は`.env`で管理し、
`.gitignore`によってGitの管理対象から除外します。

```text
.env
```

一方で、
設定例として以下のファイルをGitHubへ公開します。

```text
.env.example
```

### 公開する設定例

```text
S3_BUCKET=your-s3-backup-bucket
AWS_REGION=ap-northeast-1
AWS_PROFILE=default
```

この構成により、
実際の環境情報とポートフォリオ用のサンプル設定を分離します。

本構成におけるバックアップ処理の全体像は以下の通りです。

```text
ローカル環境
Documents / Desktop / Pictures / Downloads
        │
        ▼
launchd
毎日22:00に自動実行
        │
        ▼
s3-backup.sh
        │
        ▼
AWS CLI
aws s3 sync
        │
        ▼
Amazon S3
        │
        ├── S3 Versioning
        │
        └── Lifecycle Policy
                │
                ├── S3 Standard
                ├── S3 Standard-IA
                └── S3 Glacier Flexible Retrieval

IAM Policy
└── Least Privilege
    └── AWS CLIからAmazon S3へのアクセスを認可
```

## データ保護の考え方

本構成では、
単にAmazon S3へデータをアップロードするだけではなく、
複数の仕組みを組み合わせてデータを保護します。

```text
ローカルデータ
      │
      ▼
自動バックアップ
      │
      ▼
Amazon S3
      │
      ├── Versioning
      │     └── 上書きからの復元
      │
      ├── IAM
      │     └── 削除権限を制限
      │
      ├── aws s3 sync
      │     └── --delete を使用しない
      │
      └── Lifecycle Policy
            └── 長期保存コストを最適化
```

単一の機能に依存するのではなく、
複数の対策を組み合わせることで、
誤操作や設定ミスによるデータ損失リスクを低減します。

---

## 設計まとめ

本構成では、
Amazon S3へのバックアップ自動化に加えて、
データ保護・セキュリティ・運用性・コスト最適化を考慮しています。

主な設計ポイントは以下の通りです。

* `aws s3 sync`によるバックアップ処理
* `launchd`による毎日22:00の自動実行
* S3 Versioningによる過去バージョンの保持
* 非現行バージョンを90日間保持
* Lifecycle Policyによるストレージコスト最適化
* `aws s3 sync --delete`を使用しない
* IAMに`s3:DeleteObject`を付与しない
* IAMの最小権限の原則（Least Privilege）を適用
* バックアップ実行権限と管理者権限を分離
* `.env`による環境依存情報の分離
* 標準ログとエラーログの分離

これらの仕組みにより、
安全性・復旧性・運用性・コストを考慮した
Amazon S3バックアップ環境を構成します。
